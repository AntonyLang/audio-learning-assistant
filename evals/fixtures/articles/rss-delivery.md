# 私有订阅与音频交付：RSS 的边界

## 订阅链接是凭据

私有 RSS 的链接本身就是一个凭据。它出现在播客客户端里，可能被同步、被截图、被转发。因此服务端只保存 token 的哈希，并提供撤销与轮换；轮换之后节目 GUID 保持不变，客户端不会把同一期节目当成新的两期。

把完整 token 写进访问日志，等于把凭据复制到另一个地方。日志的保留期通常比 token 更长，这个细节经常被忽略。

## 为什么不能直接写签名 URL

对象存储的签名 URL 有有效期，通常只有几小时到几天。把它写进长期 RSS，订阅在一周后就会失效，而用户看到的只是"这一期播不了"。

稳定入口应当由自己的服务校验权限后再代理读取。存储位置发生变化时，只需要更新内部映射，订阅链接和 enclosure 地址都不必改变。

## 单段 Range 的最小契约

播客客户端拖动进度条时会发送一个单段 Range 请求。服务端需要返回 206、Content-Range 与 Content-Length，客户端才知道这一段的边界，并继续请求下一段。缺少其中任何一个，部分客户端会静默地放弃播放。

对于无法满足的范围，例如起点超过文件长度，应返回 416 并带上 Content-Range: bytes */size。多段 Range 在实际客户端中很少出现，首版可以忽略 Range 并返回完整 200，而不是返回半个 multipart 响应。

## 已发布音频保持不可变

已发布的音频应当保持不可变。修正事实错误时，创建新一期节目并在元数据里说明它纠正了哪一期，而不是悄悄替换同一个 GUID 下的文件。客户端会缓存音频，用户也无法知道内容被替换过。

不可变还带来一个实际好处：发布事务只需要校验一次音频哈希与时长，之后任何读取都不必重新计算。计划与发布分离，音频可以提前生成，等到当天预算确认后再进入清单。

## 下载次数不等于听完

RSS 客户端只告诉我们它下载了文件，通常不会回报播放进度。因此不能用下载次数推断完成率，也不应当把它当作掌握程度的证据。网页播放器的可观察区间是更可靠的信号，但它同样只说明"听过"，不说明"学会"。
