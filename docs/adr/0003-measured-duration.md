# ADR 0003：时长以实测为准，缩稿只允许一次

- 状态：已采纳
- 日期：2026-10-25

## 背景

"生成五分钟音频"最常见的实现是：按字数估算，把脚本字数控制在某个区间，然后发布。
这条路在真实语音上不成立：

- 中文口播速度随术语、数字、停顿变化，实测在 3.5–5 字/秒之间；
- TTS 引擎对数字、英文与标点的处理不一致；
- 拼接后可能多出静音或编码padding。

字数只能作为初始估计，不能作为验收标准。

## 决策

- 每次生成后用 `ffprobe` 读取最终文件 `format=duration`，以 `Decimal` 解析，
  向上取整到毫秒（`ROUND_CEILING`）；`duration_ms > 300000` 即不合格。
- 解码检查（`ffmpeg -f null -`）与时长检查都在发布之前完成，不合格不进入 `READY`。
- 超长时只允许一次缩稿：新目标 ≈ 当前字数 × (270000 / 实测毫秒)，重新组织完整论证、
  重新核源、重新合成、重新检测。
- 第二次仍超长：保留待处理稿，进入 `WAITING_REVIEW`，提示缩小主题或拆续篇。
  不截断尾部，也不用倍速凑数。
- 缩稿次数计入 `generation_runs.budget_usage.audio_revisions`，跨 attempt 累计。

## 后果

- 好处：产品承诺"不超过 5 分钟"是可验证的事实，而不是提示词里的愿望。
- 代价：需要 ffmpeg/ffprobe 运行环境；每次生成多一次解码与探测；缩稿会额外消耗 TTS 字符。
- 270 秒的目标值只是留裕量的起始参数，必须用真实语音校准，而不是硬编码字数换算。
